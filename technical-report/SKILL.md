# 技术汇报与方案讨论

产出一份可以直接发给同事阅读、开会讨论的 Markdown 文档。默认读者理解业务或研究背景，但不熟悉代码细节。

## 阅读量与取材

正文默认约 1500–2200 个中文字，配一张架构图，整体按约三页的阅读量控制；资料简单时更短，用户指定篇幅时遵从。使用 3–4 个二级章节，少用三级标题，不加目录、独立摘要、附录和重复总结来撑篇幅。

先从对话和材料确定讨论目标、受众与范围。写代码结构时检查真实目录、入口、核心调用及数据存储；只读与报告有关的部分。会影响结论的缺失信息需要澄清，其余可作为明确的假设或待讨论项。

区分已实现、已验证、拟议和待确认。用少量真实文件路径、结果或来源支持关键判断；没有依据的性能数字、排期和人员安排不写成事实。

## 组织方式

默认采用下面四章，标题随主题调整。短文可将后两章合并为一章；各章长度按重要性分配。

| 章节 | 需要回答的问题 |
| --- | --- |
| 结论与背景 | 本次建议或当前判断是什么？为什么值得讨论？范围和目标是什么？ |
| 整体方案与架构 | 系统如何工作？主要模块承担什么职责？数据或请求怎样流转？ |
| 关键取舍与依据 | 哪些设计决定影响效果、成本或维护？推荐选择的理由和代价是什么？ |
| 推进与待讨论事项 | 下一步如何验证或推进？哪些风险影响结论？需要与会者决定什么？ |

开头用一段话给出结论。正文按读者需要理解的关系展开，少按开发时间顺序记流水账。

根据任务调整重点：进展报告突出结果、偏差和下一步；方案讨论突出推荐设计与实质备选；代码结构说明突出模块边界、典型调用路径和扩展位置。不要强行编造备选方案或改造计划。

## Mermaid 架构图

默认在架构章节放一张 `mermaid` 图，通常选 `flowchart LR` 或 `flowchart TB`，表现被介绍系统的真实组成。只有时序或生命周期本身影响讨论时，再加一张小图。

图中通常保留 4–8 个主要节点；用 `subgraph` 表示有意义的边界，箭头注明关键数据或调用含义。节点使用简短中文职责名，必要时附核心模块名；用简单 ASCII 标识符和带双引号的标签，避免复杂语法。

基于实际系统重画，不套用通用的“前端、后端、数据库”结构。未实现部分在图中标明“拟议”，用虚线时解释其含义。没有实现材料时可以画拟议架构，并明确依据和假设。

图后用一小段话解释主路径与关键边界，避免逐节点重复。如果有可用的 Mermaid 预览或校验工具就检查渲染；否则核对语法、节点和连线，不声称已渲染。

## 内容取舍与交付

只保留会改变理解或决策的细节。代码结构说明选取少数关键路径，说明职责和协作，不展开完整目录树、逐函数清单、接口字段或长代码。表格用于真正需要比较的内容，通常至多一张。

风险说明具体影响与应对办法，待讨论事项写成可以回答的问题。优先使用连贯段落、具体名词和动词，避免宣传性形容词、黑话、长串列表和层层括号。

交付前确认：前三分钟能否看懂结论，图文是否一致，事实与提案是否分清，讨论事项是否具体，删去任何一段是否仍不损失信息。压缩重复内容后直接交付完整正文；只有要求落盘时才写入约定位置的一个 Markdown 文件，更新已有文档时就地修改。
